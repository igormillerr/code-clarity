# CodeClarity MCP

LLM-часть в ветке `codex/llm-workflow`: четыре Skills, независимое AI-ревью,
корреляция метрик и Rule Discovery. [Установка и запуск](docs/llm-setup.md),
[контракты и границы задач команды](docs/llm-handoff.md),
[Evals](evals/README.md), [демонстрация](docs/llm-demo.md),
[презентация](docs/presentation/README.md), [фактический статус](docs/llm-status.md).
Сервер 0.1.6 предоставляет шесть Java-метрик и единый анализ Java/Python
с автоматическим выбором адаптера по пути файла.
Для Python пока доступны Cyclomatic Complexity и явный UNSUPPORTED для Cognitive
Complexity; остальные Python-метрики ещё не реализованы. История ревью сохраняется
в `.codeclarity/review-history.json` через MCP; подтверждения исправлений записывает оператор.

Локальный Java-сервер для проверки читаемости Java- и Python-изменений между Git-коммитами. Он отдаёт Codex факты о diff, диагностике сложности и структуре функций и методов. Итоговый комментарий формулирует агент.

## Быстрый запуск

Понадобятся Java 21 или новее, Git и Codex CLI. Все программы должны быть доступны в PATH. JAR с зависимостями находится в `plugin/server/codeclarity-mcp.jar`. Разархивируй проект и укажи абсолютные пути к JAR и корню проверяемого Git-репозитория.

```powershell
codex mcp add codeclarity -- java -jar "C:\codeclarity-mcp\plugin\server\codeclarity-mcp.jar" --repo-root "C:\work\my-java-project"
codex mcp list
```

Открой новый сеанс Codex и попробуй запрос:

> Проверь читаемость Java- и Python-изменений между main и HEAD. Вызови get_changes, затем analyze_changes с возвращёнными SHA. Если изменилось больше 50 файлов, передавай их партиями через paths и объедини результаты. Для интересных методов и функций вызови get_symbol_context. Приведи файл, строки, наблюдение и минимальную правку. Укажи пропуски анализа.

Если основная ветка называется иначе, подставь её имя. Сервер работает с одним репозиторием, указанным при запуске.

## Сборка и проверка

```bash
mvn clean verify
```

`verify` собирает JAR и запускает обязательный набор локальных проверок, включая
регрессии Java, MCP, историю, LSP-протокол и проверку артефактов. Ошибка проверки
завершает сборку с ошибкой; логи и сводка находятся в `target/workflow-checks/`.
Нужны Java/Javac 21+, Git и Python 3.10+ без дополнительных пакетов.
На Windows можно указать `mvn verify -Dpython.executable=python`.
Проверки используют Java из Maven `JAVA_HOME`; модель и настоящий JDT LS не требуются.
Для сборки без полного прогона есть `mvn package`, для явного пропуска проверок
при `verify` — `-DskipTests`. CI запускает `mvn verify` без пропуска.

Тот же набор после сборки можно запустить напрямую:

```bash
python3 scripts/verify.py
```

Отдельные проверки для диагностики:

```bash
python3 scripts/mcp_smoke_test.py target/codeclarity-mcp.jar
python3 scripts/smoke_test.py target/codeclarity-mcp.jar
python3 scripts/python_worker_test.py
python3 scripts/python_smoke_test.py target/codeclarity-mcp.jar
python3 scripts/java_metrics_test.py target/codeclarity-mcp.jar
python3 scripts/core_test.py
python3 scripts/language_integration_test.py target/codeclarity-mcp.jar
python3 scripts/history_test.py target/codeclarity-mcp.jar
python3 scripts/lsp_client_test.py target/codeclarity-mcp.jar
python3 scripts/lsp_smoke_test.py
```

Java-проверки содержат исполняемые `main`: их запускает общий runner на фазе
Maven `verify`, а не Surefire. Общий интеграционный
тест проверяет оба адаптера в одном смешанном вызове MCP, автоматическую маршрутизацию,
одинаковый формат результатов, одинаковые Git-снимки, шесть Java-метрик,
положительные/нулевые/отрицательные дельты, конструкторы, методы без тела,
добавления/удаления сущностей и изоляцию ошибок файлов и языков.

На Windows для проверки можно использовать `py -3 scripts/smoke_test.py target/codeclarity-mcp.jar`. Smoke-тест создаёт временный Git-репозиторий и обращается к JAR через тот же MCP-интерфейс, что и клиент. Он проверяет инициализацию, discovery, три вызова, сравнение PMD, переименование файла, частичный анализ и чтение зафиксированного коммита при изменённом рабочем файле.

## Инструменты

| Имя | Вход | Выход |
|---|---|---|
| `get_changes` | `baseRef`, `headRef` | SHA, статус, изменённые Java/Python-файлы, диапазоны строк, предупреждения |
| `analyze_changes` | `baseSha`, `headSha`, опционально смешанный `paths` | Единый отчёт по Java и Python с автоматическим выбором адаптера |
| `get_symbol_context` | `commitSha`, `path`, `line` | SHA, путь, язык, исходник сущности, диапазон строк, вызовы, условия, статус и предупреждения |
| `get_review_history` | Без аргументов | Ревью, категории, замечания, подтверждения, статистика и примеры |
| `update_review_history` | `review` и/или `categories` | Атомарное сохранение; статус `saved`/`unchanged`, ревизия и статистика |
| `get_symbol_definition` | `path`, `line`, `column` | Определения символа через LSP, явно в текущем WORKTREE |
| `find_symbol_references` | `path`, `line`, `column`, опционально `includeDeclaration` | Использования символа через LSP, явно в текущем WORKTREE |
| `inspect_symbol_ast` | `commitSha`, `path`, `line` | Прежняя компактная форма контекста: сигнатура, строки, вызовы и условия |
| `list_java_changes` | `baseRef`, `headRef` | `baseSha` общего предка, `headSha`, старые и новые пути, диапазоны строк для обеих сторон |
| `analyze_java_changes` | `baseSha`, `headSha`, опционально `paths` | Статус анализа, изменённые методы, результаты PMD до и после, предупреждения |
| `inspect_java_method` | `commitSha`, `path`, `line` | Сигнатура метода или конструктора, его диапазон, вызовы и условия `if`, которые их окружают |
| `list_python_changes` | `baseRef`, `headRef` | SHA, изменённые `.py`-файлы и диапазоны строк |
| `analyze_python_changes` | `baseSha`, `headSha`, опционально `paths` | Изменённые функции и методы, диагностики сложности до и после, предупреждения |
| `inspect_python_function` | `commitSha`, `path`, `line` | Сигнатура функции или метода, диапазон, вызовы и окружающие ветви `if` |

Строки считаются с единицы, обе границы диапазона включены. У добавленного файла отсутствует `oldPath`, у удалённого отсутствует `newPath`. Для переименований при выборе `paths` используется новый путь, для удалений — старый.

Один STDIO-процесс предоставляет семь основных инструментов и семь
инструментов совместимости. Универсальным инструментам
не нужен параметр языка. Например, после `get_changes` можно вызвать
`analyze_changes` с `paths: ["src/Example.java", "scripts/example.py"]` и полученными
`baseSha`/`headSha`. Без `paths` обрабатываются все поддерживаемые изменения
в пределах лимита 50 записей. Неподдерживаемые расширения игнорируются;
явно выбранный неподдерживаемый или неизменённый путь вызывает ошибку запроса.

Формат `get_changes` и языковых list-инструментов:
`{baseSha, headSha, status, files, warnings}`. Формат анализа тот же;
его `files[]` содержит `{oldPath, newPath, language, changedMethods, findings, metrics, coverage}`.
Поле `language` — идентификатор выбранного адаптера. Структура одинакова для обоих
языков и универсальных/языковых инструментов. Поля `method`/`changedMethods`
сохранены для совместимости и обозначают также Python-функции.

`coverage.base` и `coverage.head` описывают покрытие изменённых строк диапазонами
поддерживаемых сущностей. Каждая сторона содержит `{status, outsideEntityLines, reason}`:
`COMPLETE` — все изменённые строки входят в такие диапазоны;
`OUTSIDE_SUPPORTED_ENTITIES` — `outsideEntityLines` перечисляет непокрытые диапазоны
(например, поля, импорты, инициализаторы); `UNKNOWN` — анализ не завершился.
Нумерация строк с единицы, границы включены. Это покрытие диапазонами сущностей,
а не оценка полноты AI-ревью или доступности всех метрик. На одной строке могут
находиться и метод, и другая декларация: гранулярность покрытия остаётся построчной.
`status: ok` у запроса не скрывает эти ограничения и не означает полного ревью.

Для методов анонимных классов владелец включает `anonymous(имяПеременной:номер)`;
для enum-констант — `enum(имя)`. Перенос строк и добавление несвязанного поля не
меняют такой идентификатор. Для выражений без имени и повторяющихся владельцев
используется лексический порядок: перестановка таких выражений может нарушить
сопоставление. Сигнатуры обычных именованных методов сохраняют прежний формат.

`get_symbol_context` возвращает
`{commitSha, path, language, status, signature, lines, source, calls, truncated, warnings}`.
`source` содержит полный текст объявления на возвращённом диапазоне строк из
указанного коммита, с переводами строк LF и без завершающего перевода строки.
Изменения рабочего каталога не подменяют этот текст. При усечении списка вызовов
возвращаются `truncated: true`, `status: partial` и предупреждение; сам исходник
сущности остаётся полным. Существующие `inspect_symbol_ast`, `inspect_java_method`
и `inspect_python_function` сохраняют прежнюю компактную структуру ответа.

Минимальный `mcp_smoke_test.py` запускает настоящий JAR через STDIO, выполняет
initialize/discovery и три универсальные операции, проверяет смешанный анализ,
пути с пробелами, диапазоны строк, исходный текст, метрики, предупреждения,
усечение контекста и ошибки аргументов. Проверка обнаружения инструментов реальным
Codex CLI: `python3 scripts/mcp_codex_smoke.py --output .codeclarity/evals/api-run`.
При отсутствии CLI в PATH передай `--codex /абсолютный/путь/к/codex`.
Сеанс использует существующую авторизацию и модель по умолчанию, режим read-only
и конфигурацию MCP только для этого процесса; установленный плагин не меняется.

Ошибки чтения, разбора, выполнения адаптера и сравнения изолируются для каждого
файла: запись остаётся в `files`, причина попадает в `warnings`, общий статус —
`partial`, остальные результаты сохраняются. У повреждённой версии нет численной
дельты. Если ошибка произошла до извлечения сущностей или при сравнении файла,
его списки результатов могут быть пустыми. Ошибки параметров запроса, SHA или
конфигурации маршрутизации возвращаются как ошибки MCP-инструмента.

`list_java_changes` возвращает список для всего сравнения. Если в списке больше 50 Java-файлов, передавай их в `analyze_java_changes` партиями до 50 путей и используй одни и те же `baseSha` и `headSha` во всех вызовах. Например, 94 файла можно проверить партиями из 50 и 44 путей.

Анализ сопоставляет методы по типу-владельцу и синтаксической сигнатуре. Он учитывает строки изменений с обеих сторон, поэтому видит правку, состоящую из удаления строк. Статусы диагностики:

- `INTRODUCED` — правило сработало в новой версии сопоставленного метода или в новом Java-файле.
- `EXISTING` — правило и его сообщение совпадают в обеих версиях.
- `CHANGED` — правило сработало в обеих версиях, но сообщение изменилось. Сверь обе диагностики.
- `RESOLVED` — правило больше не срабатывает в сопоставленном методе.
- `NO_BASE_MATCH`, `NO_HEAD_MATCH` — на соответствующей стороне не найден метод с такой сигнатурой.
- `UNVERIFIED` — одна из сторон разобрана неполно.

При ошибке отдельного файла отчёт возвращает `partial` и предупреждение. Отчёт `ok` с пустыми находками означает, что выбранные правила PMD не сработали для проверенных методов.

## Архитектура и расширение

Общая логика остаётся на Java 21. Инструменты конкретного языка скрыты за
`core/LanguageSupport.java`. Ядро не импортирует JavaParser или PMD.

- `Main.java` — сборка зависимостей и MCP API через STDIO для Java и Python.
- `git/GitRepository.java` — снимки, diff и чтение файлов любого расширения.
- `core/AnalysisService.java` — маршрутизация файлов, затронутые сущности, сравнение диагностик и метрик, изоляция ошибок и полнота отчёта.
- `core/LanguageRegistry.java` — регистрация модулей, выбор по пути файла или идентификатору языка.
- `core/model/` — диапазоны строк, сущности, диагностики, определения и значения метрик, контекст без объектов AST.
- `history/ReviewHistoryStore.java` — операции добавления ревью, категорий и подтверждений; `HistoryFileStorage` — блокировка и атомарная запись; `HistoryValidator` — контракты и целостность; `HistoryProjection` — производные статистика и примеры; `HistoryJson` — строгая сериализация. `ReviewScope` и `FeedbackEvent` задают типизированные внутренние значения.
- `lsp/LanguageServerClient.java` — общий контракт семантической навигации; `JsonRpcProcess` — ограниченный по времени STDIO JSON-RPC с Content-Length.
- `lsp/SemanticNavigationService.java` — маршрутизация к LSP и перевод координат; `languages/java/JdtLanguageServer.java` — запуск и настройка Eclipse JDT LS.
- `lsp/LanguageServerSessions.java` — ленивое переиспользование сессий, последовательные запросы к одному серверу, сброс после ошибки и закрытие при простое.
- `languages/java/JavaLanguageSupport.java` — адаптер Java, реализующий общий контракт.
- `languages/java/JavaSource.java` и `PmdAnalyzer.java` — детали работы с JavaParser и PMD.
- `languages/java/JavaParserMetrics.java` — SLOC, вложенность, параметры и возвраты Java.
- `languages/python/PythonLanguageSupport.java` — запуск Python-процесса и преобразование JSON в общие модели.
- `src/main/resources/python_analyzer.py` — разбор Python через стандартный `ast` и правило сложности.

Чтобы добавить язык:

1. Реализуй `LanguageSupport`: идентификатор языка, распознавание пути, анализ исходника и инспекцию сущности.
2. Верни общие `SourceEntity`, `Finding`, `MetricMeasurement` и `EntityContext`; объяви каталог метрик через `metricDefinitions()`. AST и объекты анализатора оставь внутри адаптера.
3. Зарегистрируй адаптер в `LanguageRegistry` в точке сборки зависимостей (`Main`).
4. Универсальный `AnalysisService(git, registry)` автоматически подключит адаптер
   к общим инструментам. Для отдельного языкового API можно использовать
   `AnalysisService(git, registry, languageId)`.

Маршрутизация использует `LanguageSupport.supports(path)`; если путь поддерживают
несколько адаптеров, реестр отклоняет неоднозначный выбор. Универсальный сервис
работает со всеми зарегистрированными языками, языковой — с выбранным адаптером.
Переименование между поддерживаемым и неподдерживаемым расширением считается
добавлением или удалением. Переименование между разными языками представляется
двумя записями: удаление старого пути и добавление нового. Выбирай эти записи по
`oldPath` и `newPath` соответственно; каждая занимает одну запись лимита партии.
Сущности разных языков никогда не сопоставляются, даже при одинаковой сигнатуре.
`SourceEntity.signature` — непрозрачный ключ сопоставления, определяемый адаптером.
Сопоставление ограничено парой файлов; переименования сущностей и переносы между
файлами автоматически не сопоставляются.

Имена MCP-инструментов `list_java_changes`, `analyze_java_changes`, `inspect_java_method`
и поля `method`/`changedMethods` сохранены для совместимости. Эти поля используются
и для Python-функций. Контекст сохраняет вызовы и окружающие ветви `if`; это не универсальная
модель управления потоком. Для будущих языков контракт контекста может потребовать расширения.

`Finding` — срабатывание правила, а не численная метрика. Численные метрики передаются
отдельно в `AnalysisResult.metrics` и сравниваются независимо от диагностик. `AnalysisResult.complete` явно отмечает
неполный анализ: отчёт будет частичным даже без текстовых предупреждений адаптера.

Проверка границы ядра без JavaParser и PMD:

```bash
python scripts/core_test.py
```

Проверка компилирует только ядро, Git-слой и искусственные адаптеры через `javac`,
затем проверяет сравнение коммитов, фильтрацию, переименования между расширениями
и языками, удаление строк, автоматический выбор адаптера, RuntimeException адаптера,
некорректные измерения, ошибки чтения и неполный анализ. Требуются JDK 21+ и Git
в PATH; при необходимости передай
`--java-home <путь-к-JDK>`.

## Поддержка Python

Для Python-анализа дополнительно нужен Python 3.10+ в PATH под именем `python`.
Зависимости из PyPI не требуются. Если интерпретатор называется `python3` или находится
в другом каталоге, задай переменную окружения `CODECLARITY_PYTHON` перед запуском сервера:

```powershell
$env:CODECLARITY_PYTHON = 'C:\Python313\python.exe'
java -jar target/codeclarity-mcp.jar --repo-root 'C:\work\my-project'
```

На Linux/macOS можно использовать `CODECLARITY_PYTHON=python3 java -jar ...`.
Значение переменной — путь или имя одного исполняемого файла, без аргументов.
Для сервера из плагина переменная должна быть доступна процессу, запускающему плагин.
Отсутствующий Python не мешает Java-анализу: Python-отчёт вернётся со статусом `partial`
и предупреждением. Ошибка инспекции возвращается как ошибка MCP-инструмента.

Пример запроса:

> Проверь Python-изменения между main и HEAD. Вызови list_python_changes, затем analyze_python_changes с возвращёнными SHA. При необходимости используй inspect_python_function. Укажи пропуски анализа.

Один вызов анализа обрабатывает до 50 файлов. Поддерживаются `.py` в UTF-8;
доступный синтаксис определяется версией выбранного интерпретатора.
Исходник разбирается через стандартный [Python ast](https://docs.python.org/3/library/ast.html),
без импорта или выполнения проверяемого кода. Процесс запускается в изолированном режиме.
У одного процесса есть лимит 15 секунд и 4 МиБ вывода.

Извлекаются обычные и `async`-функции, методы классов и вложенные функции.
Ключ сопоставления включает цепочку владельцев, имя и имена/виды параметров;
аннотации и значения по умолчанию в ключ не входят. Диапазон включает декораторы.
Вызовы извлекаются из тела функции, без декораторов, значений по умолчанию и вложенных
функций, классов или лямбд. Для вложенной функции можно запросить собственный контекст.
Код уровня модуля и лямбды не анализируются как отдельные сущности.
Инспекция возвращает до 100 вызовов, сокращая выражения и условия до 200 символов.
Окружающие `if` описывают синтаксис, а не достижимость; циклы, `match` и ранние выходы
не превращаются в условия вызова.

Собственное правило `PythonCyclomaticComplexity` срабатывает при значении **10 и выше**.
Подсчёт начинается с 1 и добавляет:

- 1 за каждый `if`, условное выражение, `for`/`async for`, `while`, `except` и `assert`;
- число операндов минус 1 за каждое выражение `and`/`or`;
- 1 за каждый генератор comprehension и 1 за каждый его фильтр `if`;
- 1 за каждый `case`, кроме безусловного захвата/`_`, и 1 за каждый guard `case`.

Вложенные функции, классы и лямбды исключены из подсчёта родительской функции.
Это собственное определение правила; оно не заявляет эквивалентность PMD или Radon.
Когнитивная сложность Python пока не вычисляется и явно имеет статус `UNSUPPORTED`.
Цикломатическая сложность возвращается для каждой извлечённой функции, включая значения ниже порога.

## Численные метрики

`analyze_java_changes` и `analyze_python_changes` возвращают дополнительное поле
`files[].metrics` для затронутых сущностей. Существующее поле `findings` сохраняет
диагностики превышения порогов; отсутствие диагностик не скрывает численные значения.

| Язык | Метрика | Источник |
|---|---|---|
| Java | `cyclomatic_complexity` | PMD `JavaMetrics.CYCLO`, настройки по умолчанию |
| Java | `cognitive_complexity` | PMD `JavaMetrics.COGNITIVE_COMPLEXITY`, настройки по умолчанию |
| Java | `function_sloc` | JavaParser, физические строки с кодом внутри объявления |
| Java | `max_nesting_depth` | JavaParser, максимальная вложенность управляющих конструкций |
| Java | `parameter_count` | JavaParser, число формальных параметров |
| Java | `return_count` | JavaParser, число собственных операторов `return` |
| Python | `cyclomatic_complexity` | Собственный алгоритм `codeclarity/python-cyclo/v1`, описанный выше |
| Python | `cognitive_complexity` | `UNSUPPORTED` |

Две Java-метрики сложности вычисляются через API PMD в том же проходе, что и диагностики,
без разбора текста сообщений. Для объявлений без тела, включая абстрактные и native-методы,
они помечаются `UNSUPPORTED`. Семантика этих вычислений остаётся семантикой PMD;
в частности, учёт вложенных объявлений может отличаться от алгоритма Python.
Описание метрик PMD: [Java metrics](https://docs.pmd-code.org/pmd-doc-7.29.0/pmd_java_metrics_index.html).

Четыре метрики JavaParser не используют пороги диагностик. Их точные определения:

- `function_sloc` (`codeclarity/java/physical-code-lines/v1`) — число физических строк,
  содержащих хотя бы один токен кода внутри объявления. Включает аннотации, сигнатуру,
  скобки и лексически вложенные объявления; исключает пустые строки и строки только
  с комментариями. Комментарии определяются по токенам JavaParser, поэтому `//` и `/* */`
  внутри строк/text block остаются кодом. Для многострочного токена считаются его
  непустые строки. Объявление без тела также имеет SLOC.
- `max_nesting_depth` (`codeclarity/java/control-nesting/v1`) — максимальная глубина
  `if`, `for`, enhanced `for`, `while`, `do`, `switch` (statement/expression), `try`
  и `synchronized` в теле. Каждый добавляет 1; исходная глубина 0. Цепочка `else if`
  остаётся на одном уровне. `catch`/`finally` принадлежат уровню своего `try`;
  обычные блоки, `case`, тернарные и логические выражения не добавляют уровень.
- `parameter_count` (`codeclarity/java/formal-parameters/v1`) — число объявленных
  параметров, включая varargs как один параметр; receiver parameter не учитывается.
  Для компактного конструктора record берутся параметры record.
- `return_count` (`codeclarity/java/owned-return-statements/v1`) — число операторов
  `return` с выражением или без него, без анализа достижимости. `yield` и неявный
  выход не считаются. Порог диагностики для Return Count не вводится.

Вложенность и возвраты исключают лямбды и члены вложенных/local/anonymous типов,
включая их инициализаторы. Вложенные методы измеряются как отдельные сущности.
У пустого тела вложенность и возвраты равны 0; у отсутствующего — `UNSUPPORTED`,
с `value: null` и причиной. SLOC и параметры доступны и без тела.
Обычные конструкторы получают все шесть метрик. Компактные конструкторы record
получают четыре JavaParser-метрики; две метрики сложности имеют `UNSUPPORTED`,
поскольку API PMD 7.29.0 не принимает `ASTCompactConstructorDeclaration`.

Каждая запись сравнения содержит `entity`, `metric`, `status`, `before`, `after` и `delta`.
Например, функция, сложность которой выросла с 2 до 3 без превышения порога, получит
`status: COMPARED`, `before.value: 2`, `after.value: 3`, `delta: 1`.

Каждая сторона содержит `definition` с полями `id`, `language`, `analyzer`, `algorithm`.
`analyzer` включает версию анализатора; для PMD она берётся из установленной библиотеки,
для JavaParser — из Maven metadata используемой библиотеки (`javaparser/3.28.2`),
для Python используется версия собственного анализатора `codeclarity-python-ast/1`.
`algorithm` фиксирует определение и настройки вычисления. При изменении собственного
алгоритма нужно обновить его идентификатор версии.

Состояния отдельного значения:

- `AVAILABLE` — получено конечное численное значение, в том числе нулевое;
- `UNSUPPORTED` — анализатор явно не поддерживает метрику для этой сущности;
- `MISSING` — сущность найдена, но анализатор не вернул измерение;
- `ERROR` — анализ версии неполон, сущность неоднозначна или измерения дублируются;
- `ENTITY_ABSENT` — соответствующей сущности нет в этой версии.

У недоступного значения нет численного `value`; `reason` объясняет причину.
Для добавленной или удалённой функции отсутствующая сторона не заменяется нулём.
Если одна версия не разобрана, её метрики считаются ошибочными и не используются для дельты.

`delta = after.value - before.value` вычисляется только для двух доступных значений
с полностью совпадающим `definition`. Статус такого сравнения — `COMPARED`.
Если определения различаются, статус — `INCOMPATIBLE`; если недоступна одна из сторон —
`UNAVAILABLE`. В обоих случаях `delta` отсутствует или равна `null`.
Метрики разных языков нельзя автоматически считать эквивалентными по совпадению `id`.

## Семантическая навигация Java (минимальный JDT LS, P1)

`get_symbol_definition` и `find_symbol_references` используют общий интерфейс
`LanguageServerClient`. Для Java реализовано подключение Eclipse JDT LS, для
Python LSP-провайдер пока не зарегистрирован. JDT LS — отдельный необязательный
дистрибутив: он не загружается при сборке или старте MCP и не входит в JAR.
Распакуй официальный дистрибутив и укажи его каталог процессу сервера:

```bash
export CODECLARITY_JDTLS_HOME=/path/to/extracted/jdtls
export CODECLARITY_JDTLS_JAVA=/path/to/compatible/jdk/bin/java
java -jar target/codeclarity-mcp.jar --repo-root /path/to/project
```

Если `CODECLARITY_JDTLS_JAVA` не задан, используется JVM текущего MCP-процесса.
Требуемая JVM зависит от версии JDT LS: текущая документация проекта требует
Java 25, приложение CodeClarity продолжает собираться с `release=21`.
Реальный тест выполнен с JDT LS 1.54.0 и JDK 25.
[Официальный запуск JDT LS](https://github.com/eclipse-jdtls/eclipse.jdt.ls#running-from-the-command-line).

Пример: `get_symbol_definition({path: "src/demo/App.java", line: 3, column: 49})`.
Входные координаты и координаты ответа — с единицы, колонки измеряются в UTF-16.
**Конец диапазона исключён**, как в LSP; это отличается от включительных
`SourceRange` в результатах AST/diff. Ответ содержит
`{scope: WORKTREE, status, language, path, line, column, locations, warnings}`.
Каждая location содержит URI, путь, `external` и диапазон start/end. Для файлов
репозитория путь относительный; внешний файл имеет абсолютный путь, а URI вида
`jdt:` возвращается с `path: null` и `external: true`. Пустые locations при `ok`
означают, что сервер не нашёл цель. `includeDeclaration` у references по умолчанию false.

LSP работает с текущими файлами рабочего дерева и не принимает commitSha.
Коммитные Git/AST/метрические инструменты продолжают работать по SHA. Во время
ревью нельзя выдавать WORKTREE-навигацию за доказательство о другом снимке;
нужно сверить файлы с проверяемым коммитом либо ограничиться AST/Git-контекстом.

Сессия JDT LS создаётся лениво и переиспользуется для последовательных запросов
одного языка в репозитории. Временные конфигурация и workspace находятся вне
репозитория. initialize, initialized и ожидание ServiceReady выполняются один раз
на сессию. Каждый запрос отправляет свежий текст через didOpen, выполняет
definition/references и didClose; одновременные запросы к одному серверу
сериализуются, чтобы не смешивать документы. Через две минуты простоя сессия
закрывается; следующий запрос создаёт новую. Ошибка или таймаут сбрасывают сессию
без скрытого повтора запроса: следующий запрос запускает сервер заново.
При закрытии выполняются shutdown и exit. При зависании процесс принудительно завершается; очистка также
предусмотрена при завершении MCP-процесса. По возможности завершаются и дочерние
процессы; запрет перечисления процессов не мешает остановке самого сервера.
Импорт Maven/Gradle, autobuild и применение workspace edits отключены. Поэтому
полноценные classpath, зависимости и навигация сложных multi-module проектов
остаются за пределами минимальной интеграции. Исходники/настройки проекта не меняются.

Таймауты задаются `CODECLARITY_LSP_STARTUP_TIMEOUT_MS` (по умолчанию 30000) и
`CODECLARITY_LSP_REQUEST_TIMEOUT_MS` (10000), допустимый диапазон 100–120000 мс.
Запуск, запись сообщений и ожидание ответов ограничены по времени; закрытие
сессии также имеет ограниченные ожидания с принудительной остановкой. Отсутствие
дистрибутива, ошибка запуска или таймаут дают `unavailable`/`timeout` с предупреждением.
Неожиданный сбой даёт `error`. Это не запускает и не отменяет анализ метрик,
не подменяет навигацию эвристикой и само по себе не делает основное ревью INCOMPLETE.

Без установки JDT LS: `lsp_client_test.py` проверяет транспорт на управляемом
тестовом сервере (включая зависание старта/запроса/записи, неверный frame, EOF,
усечённый stderr, shutdown/exit и отсутствие оставшихся процессов), а
`lsp_smoke_test.py` проверяет MCP и независимость метрик от неудачного запуска.
Проверка настоящего JDT LS:

```bash
python3 scripts/lsp_smoke_test.py --jdtls-home /path/to/jdtls \
  --java /path/to/jdk/bin/java --output .codeclarity/evals/jdtls-live.json
```

Тест проверяет definition и references между двумя Java-файлами, UTF-16 после
Unicode, точность путей/строк и сохранность проекта. Тестовый сервер не заменяет
реальную интеграционную проверку. Протокол реализован по
[LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/).

## История ревью

`get_review_history({})` читает историю репозитория, указанного при запуске сервера.
До первого сохранения возвращается пустая история с нулевой статистикой; файл
при чтении не создаётся. Первый `update_review_history` автоматически создаёт
`.codeclarity/review-history.json`. Данные сохраняются между запусками сервера.

Запрос обновления содержит `review` — полный отчёт по
[review.schema.json](plugin/contracts/review.schema.json) с `ruleDiscovery.status: NOT_RUN`,
и/или `categories` — массив `{categoryId, name, description?}`. Новые категории из
замечаний добавляются автоматически с именем, равным ID; метаданные можно обновить
отдельно. История привязана к каноническому корню репозитория.

Ревью неизменно после сохранения: одинаковые `reviewId` и содержимое возвращают
`unchanged`, не увеличивая статистику и ревизию и не переписывая файл. Другое
содержимое под тем же ID отклоняется. Повторная область SHA/языков/путей с новым
reviewId тоже отклоняется. Категории обновляются по `categoryId`.

История содержит исходные `reviews`, производные `findings`, `categories` с
`statistics` и `examples`, журнал `feedback`, общую `statistics`, `revision` и
пустой резерв `ruleCandidates`. Статистика и примеры пересчитываются из уникальных
ревью и последних подтверждений, их нельзя передать готовыми счётчиками в MCP.
`occurrenceCount` — все замечания, `detectedCount` — ожидающие решения,
`fixedCount`/`rejectedCount` — замечания с последним соответствующим решением.
Примеры включают SHA, путь/строки, описание, рекомендацию, evidence и IDs подтверждений.

Новые замечания имеют статус `DETECTED`, а исходный отчёт сохраняет
`reviewStatus: PENDING_FEEDBACK`. Исчезновение диагностики и повторный запуск
не означают исправления. MCP-инструмент не принимает feedback или `confirmed: true`.
Оператор явно записывает решение отдельной локальной CLI-командой:

```bash
java -jar target/codeclarity-mcp.jar --repo-root /path/to/repo \
  --record-feedback "review-id" "finding-id" --decision FIXED \
  --confirmed-by "Имя разработчика" --evidence "Подтверждено в коммите abc123"
```

Поддерживается также `--decision REJECTED`. Требуются существующая пара review/finding,
непустые автор и основание. Повтор идентичной команды не добавляет событие; новое
решение с новым основанием меняет текущий статус, сохраняя предыдущие события.
CLI — локальная граница доверия оператора; агент не должен вызывать её для
самоподтверждения своих замечаний. Подтверждения хранятся с `source: HUMAN` и
`authority: LOCAL_CLI` и не сбрасываются повторным сохранением ревью.

Перед чтением и сохранением проверяются JSON Schema Draft 2020-12 и целостность
ссылок, уникальность ID, статистика и примеры. Дубли ключей и лишние JSON-документы
отклоняются. Повреждённая история не перезаписывается и не заменяется пустой.
Изменение выполняется под `.codeclarity/review-history.lock`, через временный файл
в том же каталоге, `force(true)` и `ATOMIC_MOVE`; неатомарного fallback нет.
Ожидание блокировки ограничено 15 секундами, размер истории — 32 МиБ; данные
не обрезаются автоматически. Символические ссылки на файлы истории не принимаются.

Проверка `history_test.py` использует только временные репозитории и реальные MCP/CLI:
первое сохранение, категории, повтор/конфликт, некорректный JSON, feedback,
перезапуск, непрерывное чтение при атомарных заменах и четыре конкурентные JVM.
Рабочий контракт — [review-history.schema.json](plugin/contracts/review-history.schema.json),
запрос обновления — [history-update.schema.json](plugin/contracts/history-update.schema.json).
Rule Discovery уже читает/сохраняет историю; сохранение кандидатов правил остаётся
отдельной будущей операцией и не имитируется прямой записью JSON.

## Установка в составе плагина

В папке `plugin/` уже есть `plugin.json` и `mcp.json`. При сборке нового JAR замени им `plugin/server/codeclarity-mcp.jar`. Путь к JAR в `mcp.json` отсчитывается от установленного пакета через `${PLUGIN_ROOT}`.

Для запуска из плагина создай текстовый файл `~/.codeclarity/repo-root.txt` в UTF-8. Впиши туда абсолютный путь к корню проверяемого Git-репозитория. На Windows `~` соответствует домашней папке пользователя. Из корня распакованного проекта добавь каталог и установи плагин:

```bash
codex plugin marketplace add .
codex plugin add codeclarity@codeclarity-local
```

Затем открой новый сеанс. Если сервер уже был зарегистрирован для отдельной проверки, выбери один способ подключения, чтобы инструменты не отображались дважды. В пакет включены `readability-review`, `independent-review`, `metrics-correlation` и `rule-discovery`; основной сценарий запускается через `readability-review`. Порядок работы и ограничения описаны в [инструкции LLM-части](docs/llm-setup.md).

## Границы прототипа

- Сравниваются зафиксированные коммиты с исходниками до Java 21. Незакоммиченные изменения требуют отдельного режима.
- Один вызов `analyze_java_changes` обрабатывает до 50 Java-файлов. Размер отдельного исходника ограничен 250 000 символов.
- Диагностики порогов и численные метрики возвращаются отдельно. Анализ ограничен затронутыми методами и функциями; метрики всего репозитория не агрегируются.
- JavaParser показывает лексическую структуру `if`, включая ветви `then` и `else`. Для определения фактической цели вызова, динамической диспетчеризации и графа зависимостей нужна отдельная реализация.
- При смене сигнатуры или переносе метода между файлами надёжное сопоставление может отсутствовать.
