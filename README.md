# CodeClarity MCP

Локальный Java-сервер для проверки читаемости Java-изменений между Git-коммитами. Он отдаёт Codex факты о diff, диагностике PMD и структуре метода. Итоговый комментарий формулирует агент.

## Быстрый запуск

Понадобятся Java 21 или новее, Git и Codex CLI. Все программы должны быть доступны в PATH. JAR с зависимостями находится в `plugin/server/codeclarity-mcp.jar`. Разархивируй проект и укажи абсолютные пути к JAR и корню проверяемого Git-репозитория.

```powershell
codex mcp add codeclarity -- java -jar "C:\codeclarity-mcp\plugin\server\codeclarity-mcp.jar" --repo-root "C:\work\my-java-project"
codex mcp list
```

Открой новый сеанс Codex и попробуй запрос:

> Проверь читаемость Java-изменений между main и HEAD. Вызови list_java_changes, затем analyze_java_changes с возвращёнными SHA. Если изменилось больше 50 Java-файлов, передавай их партиями через paths и объедини результаты. Для интересных методов вызови inspect_java_method. Приведи файл, строки, наблюдение и минимальную правку. Укажи пропуски анализа.

Если основная ветка называется иначе, подставь её имя. Сервер работает с одним репозиторием, указанным при запуске.

## Сборка и проверка

```bash
mvn clean package
python3 scripts/smoke_test.py target/codeclarity-mcp.jar
```

На Windows для проверки можно использовать `py -3 scripts/smoke_test.py target/codeclarity-mcp.jar`. Smoke-тест создаёт временный Git-репозиторий и обращается к JAR через тот же MCP-интерфейс, что и клиент. Он проверяет инициализацию, discovery, три вызова, сравнение PMD, переименование файла, частичный анализ и чтение зафиксированного коммита при изменённом рабочем файле.

## Инструменты

| Имя | Вход | Выход |
|---|---|---|
| `list_java_changes` | `baseRef`, `headRef` | `baseSha` общего предка, `headSha`, старые и новые пути, диапазоны строк для обеих сторон |
| `analyze_java_changes` | `baseSha`, `headSha`, опционально `paths` | Статус анализа, изменённые методы, результаты PMD до и после, предупреждения |
| `inspect_java_method` | `commitSha`, `path`, `line` | Сигнатура метода или конструктора, его диапазон, вызовы и условия `if`, которые их окружают |

Строки считаются с единицы, обе границы диапазона включены. У добавленного файла отсутствует `oldPath`, у удалённого отсутствует `newPath`. Для переименований при выборе `paths` используется новый путь, для удалений — старый.

`list_java_changes` возвращает список для всего сравнения. Если в списке больше 50 Java-файлов, передавай их в `analyze_java_changes` партиями до 50 путей и используй одни и те же `baseSha` и `headSha` во всех вызовах. Например, 94 файла можно проверить партиями из 50 и 44 путей.

Анализ сопоставляет методы по типу-владельцу и синтаксической сигнатуре. Он учитывает строки изменений с обеих сторон, поэтому видит правку, состоящую из удаления строк. Статусы диагностики:

- `INTRODUCED` — правило сработало в новой версии сопоставленного метода или в новом Java-файле.
- `EXISTING` — правило и его сообщение совпадают в обеих версиях.
- `CHANGED` — правило сработало в обеих версиях, но сообщение изменилось. Сверь обе диагностики.
- `RESOLVED` — правило больше не срабатывает в сопоставленном методе.
- `NO_BASE_MATCH`, `NO_HEAD_MATCH` — на соответствующей стороне не найден метод с такой сигнатурой.
- `UNVERIFIED` — одна из сторон разобрана неполно.

При ошибке отдельного файла отчёт возвращает `partial` и предупреждение. Отчёт `ok` с пустыми находками означает, что выбранные правила PMD не сработали для проверенных методов.

## Архитектура и расширение

Общая логика остаётся на Java 21. Инструменты конкретного языка скрыты за
`core/LanguageSupport.java`. Ядро не импортирует JavaParser или PMD.

- `Main.java` — сборка зависимостей и существующий MCP API через STDIO.
- `git/GitRepository.java` — снимки, diff и чтение файлов любого расширения.
- `core/AnalysisService.java` — выбор файлов языка, затронутые сущности, сравнение диагностик и полнота отчёта.
- `core/LanguageRegistry.java` — явная регистрация и выбор модуля по идентификатору языка.
- `core/model/` — диапазоны строк, сущности, диагностики и контекст без объектов AST.
- `languages/java/JavaLanguageSupport.java` — адаптер Java, реализующий общий контракт.
- `languages/java/JavaSource.java` и `PmdAnalyzer.java` — детали работы с JavaParser и PMD.

Чтобы добавить язык:

1. Реализуй `LanguageSupport`: идентификатор языка, распознавание пути, анализ исходника и инспекцию сущности.
2. Верни общие `SourceEntity`, `Finding` и `EntityContext`; AST и объекты анализатора оставь внутри адаптера.
3. Зарегистрируй адаптер в `LanguageRegistry` в точке сборки зависимостей (`Main`).
4. Создай `AnalysisService` с идентификатором языка и подключи его к транспортному API.

Каждый сервис работает с одним выбранным языком. Переименование между поддерживаемым
и неподдерживаемым расширением считается добавлением или удалением для этого языка.
`SourceEntity.signature` — непрозрачный ключ сопоставления, определяемый адаптером.
Сопоставление ограничено парой файлов; переименования сущностей и переносы между
файлами автоматически не сопоставляются.

Имена MCP-инструментов `list_java_changes`, `analyze_java_changes`, `inspect_java_method`
и поля `method`/`changedMethods` сохранены для совместимости. Через MCP пока доступна
только Java. Контекст сохраняет вызовы и окружающие ветви `if`; это не универсальная
модель управления потоком. Для будущих языков контракт контекста может потребовать расширения.

`Finding` — срабатывание правила, а не численная метрика. Численные метрики и сравнение
их значений остаются отдельным расширением. `AnalysisResult.complete` явно отмечает
неполный анализ: отчёт будет частичным даже без текстовых предупреждений адаптера.

Проверка границы ядра без JavaParser и PMD:

```bash
python scripts/core_test.py
```

Проверка компилирует только ядро, Git-слой и тестовый язык через `javac`, затем проверяет
сравнение коммитов, фильтрацию, переименования между расширениями, удаление строк
и неполный анализ. Требуются JDK 21+ и Git в PATH; при необходимости передай
`--java-home <путь-к-JDK>`.

## Установка в составе плагина

В папке `plugin/` уже есть `plugin.json` и `mcp.json`. При сборке нового JAR замени им `plugin/server/codeclarity-mcp.jar`. Путь к JAR в `mcp.json` отсчитывается от установленного пакета через `${PLUGIN_ROOT}`.

Для запуска из плагина создай текстовый файл `~/.codeclarity/repo-root.txt` в UTF-8. Впиши туда абсолютный путь к корню проверяемого Git-репозитория. На Windows `~` соответствует домашней папке пользователя. Из корня распакованного проекта добавь каталог и установи плагин:

```bash
codex plugin marketplace add .
codex plugin add codeclarity@codeclarity-local
```

Затем открой новый сеанс. Если сервер уже был зарегистрирован для отдельной проверки, выбери один способ подключения, чтобы инструменты не отображались дважды. Если у команды уже есть skill для ревью, помести его в `plugin/skills/<имя>/SKILL.md` и добавь порядок вызова из примера запроса.

## Границы прототипа

- Сравниваются зафиксированные коммиты с исходниками до Java 21. Незакоммиченные изменения требуют отдельного режима.
- Один вызов `analyze_java_changes` обрабатывает до 50 Java-файлов. Размер отдельного исходника ограничен 250 000 символов.
- PMD сообщает срабатывания правил. Для значений ниже порога численная оценка не вычисляется отдельно.
- JavaParser показывает лексическую структуру `if`, включая ветви `then` и `else`. Для определения фактической цели вызова, динамической диспетчеризации и графа зависимостей нужна отдельная реализация.
- При смене сигнатуры или переносе метода между файлами надёжное сопоставление может отсутствовать.
