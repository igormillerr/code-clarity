# План Python Analyzer: шесть метрик

Основание: согласованное ТЗ и существующая реализация CodeClarity.
План создан 11 ноября 2026 года. Оценки — часы сосредоточенной работы одного разработчика,
включая проверку результата; ожидание согласований в них не входит.

## Цель P0

Шесть численных метрик для обычных и `async`-функций Python, доступных через общий Core:
Cyclomatic Complexity, Cognitive Complexity, Function SLOC, Max Nesting Depth,
Parameter Count, Return Count. Результат включает происхождение измерений,
`before`/`after`/`delta`, явные состояния недоступности, тесты и два воспроизводимых эксперимента.
Существующая Java-функциональность должна сохраняться.

## Решения этапа 2

- Cyclomatic Complexity: сохраняем существующий алгоритм `codeclarity/python-cyclo/v1`; изменения правил требуют новой версии определения.
- Cognitive Complexity: complexipy 8.3.0 с изоляцией текущей функции и сохранением исходной структуры. Зависимость закреплена; интеграция и 20 эталонов проверены на этапе 4.
- Function SLOC: физические строки с кодом без пустых строк, комментариев и docstring; заголовок, декораторы и код вложенных объявлений включаются. Диапазон AST сам по себе не равен SLOC.
- Max Nesting Depth: начальная глубина 0, правила управляющих конструкций зафиксированы; elif не повышает глубину цепочки, настоящий if внутри else повышает.
- Parameter Count: все виды параметров, включая self/cls и по одному за varargs/kwargs; `/` и отдельная `*` не считаются.
- Return Count: явные return текущей функции, включая голый return генератора. Вложенные функции, yield и неявный возврат не добавляются.

Полные правила, ограничения, происхождение значений и приёмочные примеры:
[спецификация метрик v1](docs/PYTHON_METRICS_SPEC.md).
Все шесть метрик, сопоставление, техническая приёмка и экспериментальные материалы реализованы.

## Обязательные интеграционные случаи

- Сбой одного вычислителя не уничтожает остальные успешно полученные метрики.
- Отсутствующее значение не подменяется нулём; ноль является допустимым доступным значением.
- Дельта вычисляется только для сопоставленных сущностей и совместимых определений метрики.
- Изменение параметров обрабатывается по однозначному квалифицированному имени Python в паре файлов; signature измерений сохраняется отдельно. Core использует непрозрачные matchingKey/флаг неоднозначности адаптера.
- Переименования и неоднозначные соответствия не сопоставляются наугад.
- Источник — Git-коммиты, незакоммиченные файлы на результат не влияют.
- Python-код анализируется без выполнения и импорта.

## Экспериментальные материалы P0

1. Уменьшение вложенности через ранние выходы: 32 фиксированных входных набора, ожидаемые результаты и реальные метрики до/после.
2. Изменение имён при неизменных метриках: 20 фиксированных входных наборов, границы численных показателей и авторская интерпретация.

По уточнению задачи подготовлены примеры, результаты прогонов и Markdown-отчёты,
без сценария живого показа или слайдов. Независимый AI-ревьюер не запускался;
иллюстративные комментарии помечены как авторские, не экспериментальные ответы модели.
Проверки поведения на 52 входных наборах не доказывают общую эквивалентность или читаемость для людей.

## P1: Pyright LSP — после готовности P0

| Шаг | Результат | Оценка |
|---|---|---|
| Прототип LSP | Инициализация, definition и references на небольшом проекте | 6–10 ч |
| Контекст коммита | Стратегия снимка целевого коммита, импорты, окружение и координаты | 10–16 ч |
| Интеграция | Ленивый запуск, таймауты, отключение, проверки отказоустойчивости | 6–8 ч |

Итого P1: **22–34 часа без резерва**, отдельно от оценки P0.
Предварительный объём — контекст целевого коммита, а не обеих версий.
Нельзя смешивать исходник одного коммита с зависимостями текущего рабочего дерева.
Недоступность LSP не блокирует метрики и выпуск P0.

## Артефакты и прогресс

- Этап 1: [отчёт проверки исходного состояния](docs/PYTHON_BASELINE_AUDIT.md).
- Этап 2: [спецификация](docs/PYTHON_METRICS_SPEC.md), [20 примеров](docs/fixtures/python_metrics_v1.json) и `scripts/python_metrics_spec_check.py`.
- Этап 3: пять численных метрик Python; 20 unit-тестов, проверка 20 эталонных примеров, MCP-проверки структурных дельт и регрессии Java/Core выполнены.
- Этап 4: шесть численных метрик Python; 28 unit-тестов без пропусков и все 20 эталонов проверены в venv с complexipy 8.3.0. MCP проверяет дельты, отсутствие библиотеки с сохранением других метрик, отсутствие интерпретатора и ошибки разбора. Java/Core продолжают проходить проверки. Установка зависимости описана в README.
- Этап 5: [правила сопоставления](docs/ENTITY_MATCHING.md); 30 Python unit-тестов и отдельные Core/MCP проверки ключей, дельт параметров, дубликатов и владельцев. Исходные сигнатуры и диапазоны обеих версий доступны в files[].matches. Численные алгоритмы и Java-правило не менялись.
- Этап 6: `python scripts/check.py` собирает текущие исходники и запускает семь наборов проверок. Все девять стадий (окружение, сборка, проверки) прошли; три негативных запуска подтвердили остановку без ложного успеха. [Техническая приёмка](docs/PYTHON_ACCEPTANCE.md) фиксирует результат, покрытие и ограничения. Maven backend в текущем окружении не запускался; проверен bundled backend.
- Этап 7: [эксперименты и результаты](experiments/python_readability/README.md); 52 входных набора, 12 сравнений метрик и два идентичных анализа на одинаковых SHA. Исходные ответы MCP сохранены в results/run.json. Единый запуск дополнен экспериментами: восемь наборов проверок, все десять стадий прошли.
- Итог P0: реализация, единый запуск проверок, README и два воспроизводимых эксперимента с фактическими результатами. Завершено 12.11.2026.
