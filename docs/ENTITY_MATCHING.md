# Сопоставление сущностей между версиями

Этап 5 завершён 12 ноября 2026 года. Правило применяется внутри пары файлов,
которую определил Git, включая распознанное переименование файла.

## Ключи языковых адаптеров

У `SourceEntity` теперь разделены:

- `signature` — идентификатор конкретного измерения и отображаемая сигнатура;
- `matchingKey` — непрозрачный для Core ключ кандидатов между версиями;
- `matchingAmbiguous` — известная адаптеру неоднозначность объявления или его владельца;
- `lines` — исходный диапазон строк сущности в соответствующем коммите.

Конструктор Java `SourceEntity(signature, lines)` и JSON без `matchingKey` сохраняют
прежнее правило: matchingKey равен signature, флаг неоднозначности по умолчанию false.
Java-адаптер по-прежнему сопоставляет только полные синтаксические сигнатуры.

Python задаёт ключ квалифицированным именем: `f`, `Service.f`, `outer.inner`.
Имена и виды параметров остаются в signature, но не входят в matchingKey.
Поэтому `f(x)` и `f(x, y)` могут образовать одну пару. Ключ не является глобальным
идентификатором репозитория: принадлежность к модулю задаётся парой путей Git.
Core не разбирает синтаксис Python и не выделяет имена из строк сигнатур.

## Алгоритм

1. Сгруппировать все сущности обеих версий файла по matchingKey.
2. Выбрать группы, хотя бы один участник которых пересекается с изменёнными строками
   соответствующей стороны. Удаление строк также учитывается.
3. Если в группе есть несколько кандидатов с любой стороны либо установлен
   matchingAmbiguous, вернуть AMBIGUOUS. Не выбирать точное совпадение сигнатуры
   раньше проверки всех кандидатов: соседний дубликат может быть неизменённым.
4. Если анализ одной из версий неполон, вернуть UNVERIFIED, не объявляя сущность удалённой/добавленной.
5. При одной сущности на каждой стороне — MATCHED; при отсутствии кандидатов с одной
   стороны — ADDED или REMOVED.
6. Для уникальной пары сравнить метрики по исходной сигнатуре каждой версии отдельно.
   Определение метрики и статусы доступности проверяются прежним алгоритмом сравнения.

Функции и классы с повторяющимся квалифицированным именем Python отмечает как неоднозначные.
Эта неоднозначность распространяется на вложенные функции и методы. Например, если
класс C объявлен дважды, уникальный по имени метод C.f всё равно нельзя надёжно
сопоставить по владельцу. Conditional definitions и getter/setter с одинаковым именем
также трактуются консервативно, без попытки определить активное объявление.

Это структурная конвенция идентичности. Она не доказывает, что два объявления с одним
именем имеют одинаковое поведение, и не разрешает динамические присваивания, aliases,
monkey patching или условия исполнения Python.

## Дополнение отчёта MCP

В каждом `files[]` появилось поле `matches`:

```json
{
  "key": "f",
  "status": "MATCHED",
  "before": [
    {"signature": "f(x)", "lines": {"startLine": 1, "endLine": 2},
     "matchingKey": "f", "matchingAmbiguous": false}
  ],
  "after": [
    {"signature": "f(x, y)", "lines": {"startLine": 1, "endLine": 2},
     "matchingKey": "f", "matchingAmbiguous": false}
  ]
}
```

Списки сохраняют всех кандидатов, включая неоднозначные. Координаты before относятся
к oldPath/baseSha, after — к newPath/headSha.

| status | Значение |
|---|---|
| MATCHED | По одному однозначному кандидату с обеих сторон |
| ADDED | На полной базовой стороне нет кандидата |
| REMOVED | На полной целевой стороне нет кандидата |
| AMBIGUOUS | Несколько кандидатов или адаптер сообщил неоднозначного владельца |
| UNVERIFIED | Одна из сторон разобрана неполно |

В `metrics[].entity`, `findings[].method` и `changedMethods` для пары используется
новая сигнатура; для удаления — старая. Если обе стороны неоднозначны, отображается
ключ группы; если лишь одна сторона имеет единственного кандидата — его сигнатура.
Исходные сигнатуры всегда доступны в matches. Входные MCP-инструменты не переименованы.

Например, Parameter Count для `f(x)` → `f(x, y)` теперь имеет before=1, after=2, delta=1
в одной записи, а не две записи с ENTITY_ABSENT.

При AMBIGUOUS соответствующая сторона метрики получает ERROR с причиной;
известное измерение однозначной противоположной стороны может сохраняться.
Дельта отсутствует, сравнение метрик UNAVAILABLE, отчёт partial с предупреждением.
Пороговые диагностики неоднозначной группы не объявляются введёнными или исправленными.
При ошибке разбора соответствующая сторона ERROR, статус пары UNVERIFIED.
Статусы сопоставления и доступность отдельной метрики независимы: ошибка complexipy
не отменяет MATCHED и не уничтожает дельты остальных метрик.

Старые статусы диагностик сохранены: например, новое срабатывание в новой функции
существовавшего файла может быть NO_BASE_MATCH; matches отдельно сообщает ADDED.
CHANGED у диагностики по-прежнему означает изменение текста сообщения, в том числе
из-за сигнатуры, а не обязательно изменение численного значения.

## Границы

- Переименование функции или её владельца автоматически не распознаётся: получаются
  отдельные ADDED/REMOVED, отсутствующие значения не заменяются нулями.
- Перенос функции между двумя разными файлами не сопоставляется. Распознанный Git rename
  файла — исключение, поскольку Git уже дал пару oldPath/newPath.
- Влияние правок вне диапазонов функций на вложенные сущности отдельно не распространяется.
- Семантическая эквивалентность и идентификация runtime-объектов не устанавливаются.

## Проверки

```bash
python scripts/core_test.py
python scripts/python_worker_test.py
python scripts/python_matching_test.py target/codeclarity-mcp.jar
python scripts/python_smoke_test.py target/codeclarity-mcp.jar

```

Нужны JDK 21+, Git и Python с `requirements-python.txt` для полного Python-сценария.
Core-тест компилируется без зависимостей от JavaParser, PMD или Python.
Проверены методы/вложенные функции, изменение параметров, дубликаты и владельцы,
conditional definitions, property getter/setter, удаление строк, изменение диагностик,
переименование файла, перенос между файлами и отсутствие complexipy.
Численные определения шести метрик на этом этапе не изменялись.
