## Единая команда

В выбранном Python-окружении должны быть установлены `requirements-python.txt`,
в PATH — JDK 21+ и Git. Из корня проекта:

```bash
python scripts/check.py
```

Если JDK не находится в PATH:

```powershell
python scripts/check.py --java-home 'C:\path\to\jdk'
```

Команда проверяет окружение, собирает **текущие исходники**, затем запускает все восемь
наборов проверок (семь на этапе 6 и добавленные эксперименты на этапе 7).
Отсутствие complexipy, несовпадение её версии или ошибка любого
этапа не превращаются в успешную приёмку. Вложенные Python-команды запускаются с
включёнными assert, даже если внешнее окружение задаёт PYTHONOPTIMIZE.

Отчёт и логи: `target/checks/report.json` и `target/checks/*.log`.
Код завершения: 0 только при полном успехе; иначе 1, последующие этапы — NOT_RUN.
Отчёт содержит версии инструментов, Git HEAD, признак незакоммиченных изменений,
SHA-256 исходников приложения/pom/requirements и SHA-256 проверенного JAR.
Эти файлы находятся в игнорируемом target и отражают последний запуск; таблица ниже
фиксирует первоначальный прогон этапа 6. После этапа 7 выполнен новый полный запуск
с десятью успешными стадиями, включая эксперименты.

## Режим сборки

- `--build-backend auto` — Maven при наличии, иначе bundled.
- `--build-backend maven` — `mvn --batch-mode clean package -DskipTests`; проверки затем
  выполняются единым скриптом, а не пропускаются из-за флага Maven.
- `--build-backend bundled` — свежая компиляция через javac с release из pom.xml;
  зависимости берутся из `plugin/server/codeclarity-mcp.jar`. Версии трёх прямых
  зависимостей проверяются по pom.properties против pom.xml. При несовпадении сборка
  останавливается. Прежние классы приложения исключаются, ресурсы заменяются текущими.
- Ни один режим не принимает существующий target-JAR за результат новой сборки.
  Если новая сборка не удалась, тесты не запускаются на старом JAR.
- Bundled-режим не заменяет Maven-разрешение всего графа зависимостей; для изменения
  зависимостей нужен Maven или заранее обновлённый совместимый комплект.
- Скрипт не устанавливает пакеты, не скачивает зависимости самостоятельно и не обновляет
  JAR плагина. Maven при необходимости может обращаться к своим репозиториям.

Дополнительно доступны `--dependency-jar`, `--report-dir` и `--timeout` (по умолчанию
180 секунд на команду). target и каталог отчёта должны оставаться внутри проекта.

## Проверка самого запуска

Выполнены три намеренно неуспешных запуска; каждый дал код 1 и success=false:

1. Неверный `--java-home` — FAILED preflight, сборка и тесты NOT_RUN.
2. Python с `-S`, без доступа к complexipy из site-packages — FAILED preflight,
   а не успешный прогон с пропущенной когнитивной метрикой.
3. Тестовый dependency-JAR с неверной версией MCP — FAILED build, все наборы тестов NOT_RUN,
   хотя ранее собранный исправный target-JAR существует.

Отчёты сохранены в target/checks-invalid-jdk, target/checks-missing-dependency,
target/checks-invalid-deps. Результаты и NOT_RUN проверены по JSON.
При разработке исправлен поиск javac в Windows: программа теперь разрешается в абсолютный
путь с учётом выбранного JDK до запуска subprocess.

## Что не подтверждено этим этапом

- Runtime JDK 21, другие версии Python и другие ОС отдельно не прогонялись.
- Maven backend подготовлен, но не проверен исполнением в этом окружении.
- Пакетная проверка Python использует файлы без функций и подтверждает границу/маршрутизацию,
  а не производительность complexipy на 51 большом модуле.
- Нет доказательства семантической эквивалентности рефакторинга или объективной оценки читаемости.
- Лимиты процесса и аварии нативного модуля не превращены в изолированные подпроцессы метрик.
- Эксперименты добавлены на этапе 7, вне первоначального прогона этой таблицы. Проверка
  человеком полезности AI-комментариев и Pyright по-прежнему не выполнялись.

Численные алгоритмы и код приложения на этапе 6 не менялись. Содержимое классов и ресурсов
комплектного plugin-JAR сверено с новой проверенной сборкой; переупаковка plugin-JAR не требовалась.
