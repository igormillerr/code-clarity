# Исправления аудита Java Core

Дата: 12.11.2026. Ветка: `codex/unified-mcp-api-fixes`, основа:
`codex/unified-mcp-api` / `2a6b6bb867236b7ef14f3b34374ba696a71fdf3e`.
Версия исправленного сервера: **0.1.7**.

## Изменения

1. **Граница хранения истории.** Для `.codeclarity`, файла истории и lock-файла
   проверяются фактический канонический путь, тип файла и отсутствие перенаправления.
   NTFS junction и symlink отклоняются до операции с историей. Проверки повторяются
   под блокировкой; временный файл также проверяется и открывается с NOFOLLOW_LINKS.
2. **Конкурентные операции Windows.** MCP-чтение и read-modify-write используют
   одну межпроцессную блокировку. Канал чтения закрывается до JSON/schema validation.
   Краткий Windows sharing conflict при замене получает ограниченный повтор в течение
   двух секунд; сохраняются fsync и ATOMIC_MOVE без неатомарного fallback.
   Повреждённый JSON не перезаписывается. Чтение отсутствующей истории не создаёт каталог.
3. **Кандидаты правил.** `propose_rule_candidate({candidate: ...})` сохраняет только
   `PROPOSED`, проверяя минимум три разные source/snapshot occurrences одной категории
   и минимум два разных повторения с последним внешним HUMAN/LOCAL_CLI FIXED.
   Findings, feedback и примеры должны ссылаться на сохранённые данные.
   Одинаковый ID/payload возвращает `unchanged`, конфликт отклоняется; эквивалентные
   предложения дедуплицируются по категории и нормализованному заголовку либо набору
   supporting IDs. Смысловую эквивалентность проверяет Skill.
   MCP не принимает подтверждения, счётчики или активацию правила.
   Последующее REJECTED меняет текущую статистику, сохраняя историческое предложение
   и его исходные ссылки; повтор того же сохранённого ID остаётся идемпотентным.
4. **Windows-кодировка.** LSP smoke явно использует UTF-8 для файлов и MCP stdio.
   Глобальный UTF-8 режим не требуется. Проверка чистоты Git теперь проверяет
   настоящий stdout команды вместо возвращавшей None функции-обёртки.
5. **Идентичность анонимных Java-владельцев.** Адаптер помечает позиционные владельцы
   через необязательный `SourceEntity.matchingWarning`. При предупреждении любой
   стороны Core сохраняет измеренные значения, возвращая сравнение `UNAVAILABLE`,
   `delta: null`, предупреждение и PMD-диагностики `UNVERIFIED`.
   Это относится также к повторяющимся локальным именам и владельцам-инициализаторам.
   Однозначные именованные владельцы продолжают сравниваться.

Новая production-схема: [rule-candidate.schema.json](../plugin/contracts/rule-candidate.schema.json).
Примеры вызовов и полный контракт находятся в [README](../README.md) и
[MCP compatibility](../plugin/contracts/mcp-compatibility.md).

## Проверка

Windows, OpenJDK 21, Python 3.13.2. Компиляция и packaging выполнены через
`mvn clean verify`. После обновления ожидаемого списка Tools в smoke-тесте
повторный `mvn verify` завершился **BUILD SUCCESS: 16/16 проверок**.
Java-тесты с main запускаются общим verify runner; Surefire сам их не исполняет.

- Реальный STDIO MCP: discovery, Java/Python, partial failures, committed snapshots.
- История: создание, повтор, конфликт, повреждённый JSON, перезапуск, подтверждения.
- Три NTFS junction: каталог истории, history-файл и lock-файл; внешние данные не меняются.
- Один MCP-читатель и четыре JVM-писателя: 12 записей и 12 повторов,
  конечный набор содержит все подтверждённые записи без дублей.
- Внешний raw reader удерживает Windows-файл до появления временного файла записи;
  последующая атомарная замена успешно повторяется после закрытия читателя.
- Кандидаты: подтверждённые refs, latest FIXED, повтор, конфликт, дедупликация,
  отказ при выдуманных refs/examples, synthetic, ACTIVE и клиентских счётчиках.
- Java: вставка, перестановка, удаление и замена анонимных выражений не дают
  уверенную дельту; PMD-диагностика сложного callback остаётся UNVERIFIED.
- LSP smoke отдельно проходит при `PYTHONUTF8=0`, locale/stdout CP1251.

Сводка и SHA-256 поставляемого JAR:
[java-core-fixes.json](../evals/results/java-core-fixes.json).
Собранный JAR скопирован в `plugin/server/codeclarity-mcp.jar`.

## Передача интеграции

Проверки выполнялись на одноразовых тестовых репозиториях. Пользовательская история,
установленный плагин и ветка `codex/llm-workflow` сохраняют прежнее состояние.
Актуальные Python6/EntityMatcher и workflow 0.3.2 находятся в `codex/llm-workflow`;
при последующем объединении нужно сохранить matchingKey/matchingAmbiguous вместе
с новым matchingWarning и launcher 0.3.2. Python-анализатор этой ветки остаётся
версией из исходной Java-ветки.

Настоящий JDT LS на Windows и новый сеанс установленного Codex-плагина остаются
NOT_RUN. Проверены MCP и изоляция отсутствующего JDT LS; сохранённые старые
авторские Codex/JDT receipts не заменялись новыми утверждениями.
