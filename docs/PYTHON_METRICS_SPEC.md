# Спецификация метрик Python v1

Дата: 11 ноября 2026 года. Этап 2 [плана](../IMPLEMENTATION_PLAN.md).
Статус: правила и приёмочные примеры зафиксированы для реализации P0.
После этапа 4 в приложении реализованы все шесть численных метрик.
Cognitive Complexity требует установленной complexipy 8.3.0; ошибка зависимости отражается
в её собственном состоянии, не уничтожая остальные пять значений.

## 1. Общие правила

- Единица анализа — `FunctionDef` или `AsyncFunctionDef`, включая методы и вложенные функции.
- Все шесть значений — неотрицательные целые числа; CC начинается с 1, остальные могут быть 0.
- Числа вычисляются независимо от порогов диагностик. Для CC сохраняется существующий порог 10;
  новых порогов и общего readability score в этом этапе не вводится.
- Значения относятся к исходнику выбранного Git-коммита. Проверяемый код не выполняется и не импортируется.
- Цикломатическая и когнитивная сложность, вложенность и возвраты считаются по телу текущей
  функции. Заголовок, декораторы, аннотации, значения параметров по умолчанию и вложенные
  области функций, классов и лямбд в эти четыре метрики не входят.
- Function SLOC измеряет физический объём функции: включает её заголовок, декораторы и
  исходный текст вложенных объявлений. Поэтому SLOC родителя и вложенной функции пересекаются.
  Их нельзя суммировать как независимые объёмы репозитория.
- Parameter Count учитывает только параметры текущего объявления.
- Лямбды и модульный код не выделяются как самостоятельные сущности P0.
- Применяется одна схема для `def` и `async def`; `async` сам по себе не увеличивает метрики.
- Изменение правил требует новой версии `algorithm`. Результаты разных определений не получают дельту.

## 3. Cyclomatic Complexity

Сохраняем действующий алгоритм, не заменяя его Radon или другой реализацией:

| Конструкция | Прибавка |
|---|---:|
| Базовое значение функции | 1 |
| `if`, каждый `elif`, условное выражение `a if condition else b` | +1 |
| `for`, `async for`, `while` | +1 |
| Каждый `except` / обработчик `except*` | +1 |
| `assert` | +1 |
| `and`/`or` | Число операндов узла BoolOp минус 1 |
| Каждый генератор comprehension | +1 |
| Каждый фильтр `if` comprehension | +1 |
| Каждый case, кроме безусловного wildcard/capture | +1 |
| Guard case | +1 дополнительно |

`else`, `try`, `finally`, `with`, `async with`, `await`, `return`, `yield`, `break`, `continue`
и `match` сами по себе ничего не добавляют. Альтернативы шаблона `case 1 | 2` отдельно
не увеличивают значение. Безусловным capture/wildcard здесь считается `MatchAs` без
вложенного pattern и без guard; это точное правило существующей версии алгоритма.
Рекурсия сама по себе не добавляет CC. Это структурный счётчик, а не построение полного CFG.

## 4. Cognitive Complexity

Используем **complexipy 8.3.0**, не называя результат точной эквивалентностью Sonar или PMD.
Описание API: [complexipy Python API](https://complexipy.com/api-reference/).

Проверенный способ вызова — `code_complexity` со значениями
`check_script=False`, `no_ignore=True`, `with_plans=False`.
Это позволяет получать числа без учёта inline ignore и без генерации планов рефакторинга.

### Обнаруженное ограничение и выбранная адаптация

На пробном файле с `outer` и вложенной `inner` прямой вызов библиотеки вернул только
`outer` со значением 1: вложенная логика попала в оценку внешней функции.
Поэтому анализ всего файла с простым сопоставлением списка результатов не подходит нашему контракту.
Это наблюдение на конкретном примере, а не утверждение обо всех вариантах вложенных объявлений.

Для каждой найденной нашим AST функции:

1. Берём её собственный исходный сегмент от `def`/`async def`, без её декораторов.
2. Вложенные объявления функций и классов, включая их декораторы, заменяем на `pass`;
   выражения `lambda` — на `None`. Сохраняем переводы строк и исходную структуру остального кода.
3. Не выполняем преобразованный код. Передаём его только статическому анализатору.
4. Требуем единственный результат функции и привязываем его к исходной сущности.
   Для вложенной именованной функции отдельно выполняем такую же процедуру.
5. Число возвращаем без изменения. Условия, циклы, логические последовательности,
   match, рекурсию и прочие особенности оценивает закреплённая версия библиотеки.

Заголовок сохраняется для синтаксического разбора; его выражения не увеличивают
метрику тела. На этапе 4 проверены аннотации, defaults и декораторы с условными выражениями.
При последующих несовпадениях требуется пересмотр адаптации и версии, а не скрытая правка числа.

**Не использовать `ast.unparse` для восстановления всей функции:** эксперимент показал,
что он превращает `else: if` в `elif`. На нашем примере это изменило оценку с 4 до 2.
Исходная цепочка `elif` получила 3. Прототип с сохранением текста подтвердил ожидаемые
значения 4 и 3 соответственно. При работе с координатами нужно преобразовывать UTF-8
byte offsets AST в позиции строк Python, не смешивая их с символьными колонками.

В выбранной версии пример `match_guard` получает когнитивную сложность 1, хотя наш CC равен 4.
Это результат конкретной библиотеки, а не ошибка, которую мы компенсируем добавлением баллов.
Отдельные тесты проверяют ошибку вычислителя и сохраняют другие метрики при его отказе.
Рекурсивный вызов `f(...)` в нашем примере добавляет балл, а `self.f(...)` у async-метода
закреплённая библиотека не считает таким же образом. Это её семантика, а не обещание
полного семантического разрешения рекурсивных вызовов.

Если библиотека отсутствует, её вычисление завершилось ошибкой или результат невозможно
однозначно привязать к функции, только Cognitive Complexity получает `ERROR`/`MISSING`
с причиной. Значение не подменяется нулём и не вычисляется LLM.

## 5. Function SLOC

Это **число физических строк с кодом**, не число операторов и не длина диапазона AST.

- Диапазон: от первого декоратора текущей функции (или `def`) до конца функции включительно.
- Включаем декораторы, заголовок, аннотации, defaults и весь физический код внутри диапазона,
  в том числе вложенные функции, классы и лямбды.
- Исключаем строки без значимых токенов: пустые, только комментарии и только docstring.
  Docstring распознаётся по AST как первое выражение со строковой константой в теле
  функции, класса или модуля, а не как любая отдельно стоящая строка.
- Исключаем docstring вложенных функций и классов внутри диапазона тоже.
- Значимые токены определяем через `tokenize`; COMMENT, NL, NEWLINE, INDENT, DEDENT,
  ENCODING и ENDMARKER сами по себе строку кодом не делают.
- Каждая физическая строка с хотя бы одним оставшимся токеном учитывается один раз.
  Строки только с закрывающими скобками, запятыми или `:` считаются строками кода.
- Многострочный строковый литерал, который не является docstring, учитывается по всем
  физическим строкам своего токена, даже если внутри него есть визуально пустая строка.
- Если docstring находится на одной строке с заголовком или другим оператором,
  оставшийся код сохраняет строку в подсчёте. Не исключаем целую строку по совпадению номера.
- Разделитель `;` непосредственно после docstring не считается самостоятельным кодом.
  Поэтому строка только с `"doc";` исключается, а строка с `"doc"; return 1` учитывается.
- Кавычки, `#` внутри литерала и экранированные переводы строк не трактуются эвристиками;
  ориентируемся на токенизацию и диапазоны AST с нормализованными координатами.

Пример `def f(): "doc"; return 1` имеет SLOC=1. У функции с docstring и комментарием
из примера `decorator_docstring` SLOC=5, хотя её исходный диапазон занимает 8 строк.

## 6. Max Nesting Depth

Это максимальная **синтаксическая глубина выбранных управляющих конструкций** в теле,
не глубина дерева AST и не число отступов. Начальная глубина — 0.

| Конструкция | Правило |
|---|---|
| if | Внутри узла глубина +1; ветви then/else находятся на одном уровне |
| elif | Продолжение той же цепочки, без дополнительного уровня |
| Настоящий if внутри else | Новый уровень; отличаем его от elif по исходному ключевому слову |
| for, async for, while | +1; loop else на той же глубине, что тело цикла |
| with, async with | +1 за оператор, независимо от числа context items |
| try / try* | +1 за общую конструкцию; try body, except/except*, else и finally — параллельные ветви одной глубины |
| match | +1; case и guard сами по себе уровень не добавляют |
| Условное выражение | +1 |
| Comprehension / generator expression | +k, где k — число генераторов; фильтры сами по себе глубину не добавляют |

Управляющие узлы, находящиеся внутри этих конструкций, увеличивают глубину относительно
их уровня. Это относится и к выражениям условия/итерации. Для comprehension вложенные
выражения обходятся на уровне d+k; это выбранная синтаксическая конвенция, а не порядок
их исполнения. Вложенная comprehension добавляет свои генераторы к текущему уровню.
BoolOp, await, return, yield, assert, обычные вызовы и блок функции уровень не добавляют.
Вложенные def, class и lambda вместе с их заголовками исключаются из обхода.

Примеры: последовательные if → 1; три вложенных if → 3; if/elif/else → 1;
async with → async for → if → 3; try с if в теле → 2; comprehension с двумя генераторами → 2.

## 7. Parameter Count

Формула: `len(posonlyargs) + len(args) + len(kwonlyargs) + bool(vararg) + bool(kwarg)`.

- `self` и `cls` учитываются, как и любой другой явно объявленный параметр.
  Не пытаемся угадать binding или смысл имени без семантического анализа.
- Каждый `*args` и `**kwargs` даёт 1, независимо от количества аргументов при вызове.
- Разделители `/` и отдельная `*` не считаются параметрами.
- Defaults, аннотации, возвращаемый тип и type parameters не увеличивают число.

У `def f(self, a, /, b=0, *args, flag=True, **kwargs)` Parameter Count=6.
Добавление параметра меняет метрику и отображаемую сигнатуру, но matchingKey Python
остаётся квалифицированным именем. После этапа 5 однозначные пары имеют численную дельту.
Дубликаты и неоднозначные владельцы не сопоставляются наугад.

## 8. Return Count

Число узлов `Return` в собственной области функции, включая голый `return`.
Учитываем все синтаксические return, даже если ветка недостижима; не строим CFG.
Не учитываем неявный возврат None, yield/yield from, raise или return вложенной функции.
Для генератора действует то же правило: yield не добавляет return, явный return добавляет 1.

## 11. Ошибки и совместимость

Сопоставление отделено от сигнатур измерений. [Контракт matchingKey и matches](ENTITY_MATCHING.md)
описывает точное правило Java, квалифицированные имена Python, неоднозначные владельцы
и сохранение сигнатур/диапазонов обеих версий. Добавление параметра не мешает сравнению
однозначной пары; определения самих численных метрик на этапе 5 не менялись.

- Ошибка разбора файла: сущности неизвестны, отчёт partial, значения не фабрикуются.
- Ошибка одного вычислителя: partial с причиной, но успешные значения остальных сохраняются.
- В контракте `complete` означает полноту сущностей и диагностик, а не доступность всех метрик.
  Ошибка complexipy оставляет `complete=true`, устанавливает ERROR/MISSING у её измерений
  и добавляет warnings; Core сохраняет остальные значения, но возвращает отчёт partial.
- `UNSUPPORTED` — действительно неподдерживаемая метрика/конструкция; отсутствие нужного
  установленного пакета для заявленной поддержки — `ERROR`, а не ложный ноль.
- Неоднозначное соответствие и дублирующиеся измерения — ошибка/предупреждение, без дельты.
- Новая/удалённая сущность — `ENTITY_ABSENT` на отсутствующей стороне.
- `MISSING` — сущность есть, но вычислитель не вернул ожидаемое измерение.
- Общие поля метрик сохраняются; новый транспорт и второй MCP-сервер не требуются.
- Структурные метрики Python не добавляются автоматически в Java-модуль.
