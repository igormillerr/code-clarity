# Python: эксперименты с изменениями кода

Два контролируемых эксперимента для отчёта, без слайдов и живого показа.
Код и ожидаемые значения заданы в репозитории; результаты получены фактическим запуском
CodeClarity через MCP на двух Git-коммитах.

## Материалы

- [Манифест](manifest.json) — входные наборы, ожидаемые результаты поведения и шесть метрик.
- [Структура: до](structure/before.py), [после](structure/after.py).
- [Имена: до](naming/before.py), [после](naming/after.py).
- [Зафиксированный машинный отчёт](results/run.json) — реальные ответы MCP, SHA коммитов,
  определения метрик, хеши исходников/JAR, контекст функций и результаты каждого входного набора.
- [Автоматическая сводка](results/summary.md) — таблицы фактически полученных значений.

Зафиксированный результат — снимок успешного прогона, а не автоматически обновляемый
источник истины после будущих изменений кода. Обычные проверки пишут новые результаты
в target/experiments, не перезаписывая этот снимок.

## Воспроизведение

Нужны JDK 21+, Git и Python с `requirements-python.txt`.
Весь проект, включая эксперименты, проверяется одной командой:

```bash
python scripts/check.py
```

При отсутствии JDK в PATH передай `--java-home <путь-к-JDK>`.
Единый запуск заново собирает текущие исходники приложения; после этапа 7 он включает
восемь наборов проверок, всего десять стадий с проверкой окружения и сборкой.

Если актуальный JAR уже собран, только эксперименты:

```bash
python scripts/python_experiments.py
```

Поддерживаются `--jar`, `--java-home` и `--output-dir`.
По умолчанию JSON и Markdown сохраняются в target/experiments; код 0 означает успех,
ошибка измерений, поведения или зависимости даёт код 1 и success=false в отчёте.
Для осознанного обновления снимка можно передать
`--output-dir experiments/python_readability/results`, затем проверить diff.

Скрипт создаёт временный Git-репозиторий с before/after-версиями, фиксированными датами
и авторами коммитов, отключёнными локально hooks и преобразованием CRLF. Исходники снимков
нормализуются в LF. Затем выполняет list → analyze → inspect и повторяет analyze:
два ответа для тех же SHA должны совпасть полностью.

Тест поведения намеренно исполняет **только эти контролируемые фикстуры** через runpy.
Сам анализатор по-прежнему не импортирует и не выполняет код проверяемого репозитория.
Рабочие ветки и коммиты основного проекта эксперимент не меняет.

## 1. Изменение структуры: вложенные проверки и ранние выходы

`shipping_fee(order)` возвращает условную стоимость доставки в целых единицах либо None.
Вход — обычный dict со всеми четырьмя полями:

- paid и priority — bool;
- items — int; выбранные значения −1, 0, 1, 3;
- destination — local или remote.

Правило задачи: неоплаченный или пустой заказ не получает стоимость; для remote
стоимость 1500, для local — 900 при priority и 500 иначе.
Это учебные константы, не реальные тарифы.

Before накапливает результат внутри четырёх уровней if. After сначала завершает
неподходящие случаи, затем возвращает стоимость. В манифесте 32 комбинации выбранных
входных значений. Обе версии возвращают ожидаемый результат нужного типа и не изменяют вход.

| Метрика | До | После | Дельта |
|---|---:|---:|---:|
| Cyclomatic Complexity | 5 | 5 | 0 |
| Cognitive Complexity | 12 | 4 | −8 |
| Function SLOC | 12 | 10 | −2 |
| Max Nesting Depth | 4 | 1 | −3 |
| Parameter Count | 1 | 1 | 0 |
| Return Count | 1 | 5 | +4 |

**Наблюдение:** количество учитываемых развилок не изменилось, но структура стала
менее вложенной. Не все показатели уменьшаются: возвратов стало больше.
Эти данные не дают основания вводить правило «меньше return всегда лучше» или суммировать
дельты в универсальную оценку качества. Влияние на скорость понимания человеком не измерялось.

## 2. Изменение имён при неизменных метриках

`remaining` вычисляет остаток вместимости после бронирования: max(capacity − reserved, 0).
Входы — неотрицательные int; порядок позиционных аргументов в обеих версиях одинаков.

В before параметры названы a/b, промежуточное значение — c. В after используются
capacity, reserved и available. Тело сохраняет ту же структуру.
Проверены 20 комбинаций capacity из {0, 1, 10, 25} и reserved из {0, 1, 5, 25, 30}.
Обе версии вернули ожидаемые значения правильного типа.

| Метрика | До | После | Дельта |
|---|---:|---:|---:|
| Cyclomatic Complexity | 2 | 2 | 0 |
| Cognitive Complexity | 1 | 1 | 0 |
| Function SLOC | 5 | 5 | 0 |
| Max Nesting Depth | 1 | 1 | 0 |
| Parameter Count | 2 | 2 | 0 |
| Return Count | 2 | 2 | 0 |

**Наблюдение:** численные показатели не оценивают качество выбранных имён. CodeClarity
при этом видит сам diff и смену сигнатуры a/b → capacity/reserved; нулевые дельты не означают
отсутствия изменения. Благодаря matchingKey обе версии остаются сопоставленной функцией.
Предположение, что новые имена понятнее, опирается на заданное назначение функции и остаётся
человеческой интерпретацией; оно не подтверждено исследованием с участниками.

## Замечания и AI: что реально получено

В обоих примерах CC ниже выбранного порога 10, поэтому пороговых диагностик нет.
Это не означает «идеально читаемый код»: численные изменения первого примера всё равно видны.

Независимый AI-ревьюер в эксперименте **не запускался**. В JSON указано ai_review.status=not_run.
Ниже — авторские иллюстрации пояснений, а не сохранённые ответы отдельного AI-прогона:

> Структура: вложенность уменьшилась с 4 до 1 при неизменной CC=5. Ранние выходы
> выделили неподходящие случаи, но увеличили число return. По проверенным входам
> результаты совпадают; общая эквивалентность этим тестом не доказана.

> Имена: показатели остались прежними. В контексте расчёта остатка вместимости имена
> capacity и reserved объясняют роли аргументов лучше, чем a и b; метрики этого не измеряют.

Нельзя на основании этих материалов утверждать, что AI обнаружил проблему, превосходит
линтеры или улучшил качество ревью. Для такого вывода нужен отдельный зафиксированный
эксперимент с моделью, промптом, контрольными вариантами и оценкой ответов.

## Что подтверждено и что не подтверждено

- Подтверждены реальные ответы Git/MCP, шесть численных before/after/delta и совпадение
  двух анализов на одинаковых SHA/окружении.
- Подтверждено совпадение поведения с заданными ответами на 52 входных наборах
  (104 вызова функций: before и after для каждого), без изменения входов.
- Проверен полный перебор выбранных конечных наборов, а не всех возможных Python-значений.
- Не доказаны общая эквивалентность, улучшение читаемости для людей, новизна продукта
  или преимущество над другими анализаторами.
- Это два учебных примера, не репрезентативный benchmark проектов или исследование пользователей.
- Версии инструментов и фактический JAR фиксируются в отчёте. При смене алгоритма,
  зависимости или исходников нужно повторить прогон и пересмотреть ожидаемые числа.
